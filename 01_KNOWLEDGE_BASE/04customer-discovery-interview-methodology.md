# متدولوژی مصاحبه Customer Discovery برای پروژه‌های وب‌سایت
### سند مرجع برای طراحی منطق AI Agent مصاحبه‌گر با مشتری

---

## نحوه استفاده از این سند توسط Agent

این سند برای تبدیل مستقیم به **منطق مصاحبه (Interview Logic)** نوشته شده: هر بخش شامل اصل، دلیل، و قانون قابل‌اجرا (Rule) است. بخش پایانی یک **فلوی کامل مصاحبه + سیستم برچسب‌گذاری پاسخ‌ها** ارائه می‌دهد که می‌تواند مستقیم به state machine یک AI Agent تبدیل شود.

## ۱. اصول Discovery چیست؟

### اصل بنیادین: «همه به شما دروغ می‌گویند» (نه از روی بدخواهی)
مبنای روش Mom Test این است که آدم‌ها معمولاً از سر ادب، همدلی، یا تمایل به تأیید، پاسخ‌های مثبتِ گمراه‌کننده می‌دهند — نه چون قصد فریب دارند. وظیفهٔ مصاحبه‌گر طراحی سؤال‌هایی است که حتی این تمایل طبیعی به ادب‌ورزی هم نتواند پاسخ را منحرف کند.

### سه قانون طلایی Mom Test
1. **دربارهٔ زندگی مشتری صحبت کن، نه دربارهٔ ایدهٔ خودت.** تا وقتی مشتری از «راه‌حل» یا «محصول» شما خبردار نشده، نمی‌تواند به آن واکنش مؤدبانه نشان دهد. معرفی زودهنگام ایده، مکالمه را «آلوده» می‌کند.
2. **دربارهٔ گذشتهٔ مشخص بپرس، نه آیندهٔ فرضی.** «آیا از فلان قابلیت استفاده می‌کردی؟» بی‌ارزش است؛ «آخرین‌باری که با این مشکل مواجه شدی چه کردی؟» واقعیت می‌دهد.
3. **بیشتر گوش بده، کمتر حرف بزن.** هدف یادگیری است نه فروش؛ سکوت و فضادادن به مصاحبه‌شونده کیفیت پاسخ را بالا می‌برد.

### Discovery یک فرآیند تکرارشونده است، نه یک رویداد یک‌باره
Discovery نباید «چک‌لیستی که یک‌بار انجام می‌شود» تلقی شود؛ باید حلقهٔ بازخورد مداوم باشد: فرضیه → مصاحبه → اصلاح فرضیه → مصاحبه بعدی.

### تفاوت Customer Discovery و Customer Validation (مدل Steve Blank)
- **Discovery:** فهمیدن اینکه مسئله واقعاً وجود دارد و برای چه کسی مهم است (کاوش باز).
- **Validation:** سنجش اینکه آیا راه‌حل پیشنهادی واقعاً خریداری/استفاده می‌شود (تأیید فرضیه). این دو نباید در یک مکالمه با هم قاطی شوند؛ در Discovery هنوز نباید راه‌حل مطرح شود.

### جدول قانون برای Agent
| اصل | قانون اجرایی برای Agent |
|---|---|
| عدم آلودگی مکالمه | تا رسیدن به مرحلهٔ مشخص در فلو، هیچ اشاره‌ای به «راه‌حل/ویژگی پیشنهادی» نکن |
| اولویت گذشته بر آینده | هر سؤالی که شکل «آیا دوست داری X را داشته باشی؟» دارد را به «آخرین‌باری که با این وضعیت روبه‌رو شدی چه کردی؟» بازنویسی کن |
| گوش‌دادن فعال | بعد از هر پاسخ حداقل یک سؤال پیگیری («چرا؟»، «بیشتر توضیح بده») بپرس پیش از رفتن به سؤال بعدی |
| ماهیت تکرارشونده | در پایان هر مصاحبه، فرضیه‌های به‌روزشده را ثبت کن؛ سؤال‌های مصاحبهٔ بعدی بر اساس آن اصلاح شود |

## ۲. چگونه سؤال درست انتخاب کنیم؟

### آزمون «آخرین‌بار» (Last Time Test)
اگر سؤالی را نتوان از حالت «آیا دوست داری...» به «آخرین‌باری که... چه اتفاقی افتاد؟» تبدیل کرد، آن سؤال ترجیح می‌سنجد نه رفتار — و باید بازنویسی یا حذف شود.

### ویژگی‌های یک سؤال خوب
- **باز (Open-ended):** با «چطور»، «چرا»، «چه چیزی» شروع می‌شود، نه بله/خیر.
- **خاص و رفتاری:** به یک موقعیت واقعیِ گذشته اشاره دارد، نه تعمیم کلی («معمولاً چطوری...» ضعیف‌تر از «هفتهٔ پیش دقیقاً چه کردی؟»).
- **فاقد فرض پیشینی (Assumption-free):** سؤالی مثل «چطور سیستم X را با Y یکپارچه می‌کنید؟» از قبل فرض کرده که هر دو سیستم را دارند. باید با سؤال بازتر شروع کرد: «برای این فرآیند از چه ابزارهایی استفاده می‌کنید؟»
- **بدون واژه‌های هدایت‌کننده:** عباراتی مثل «آیا فکر نمی‌کنید...»، «مگر نه که...» را حذف کن — این‌ها Leading Questions هستند و پاسخ را در خود دارند.
- **دربارهٔ هزینهٔ واقعی:** بهترین سؤال‌ها نشان می‌دهند مشکل چقدر واقعی است — «آیا تا حالا برای حل این مشکل پول/زمان صرف کرده‌اید؟» (زمان و پول، سیگنال درد واقعی‌اند، نه صرفاً بیان نارضایتی).

### جدول تبدیل سؤال ضعیف به قوی
| سؤال ضعیف (فرضی/نظرخواهی) | سؤال قوی (رفتاری/واقعی) |
|---|---|
| آیا از قابلیت X استفاده می‌کنید؟ | آخرین‌باری که به این مشکل برخوردید کِی بود؟ |
| آیا سایت جدید را دوست دارید؟ | وقتی وارد سایت می‌شوید معمولاً دنبال چه چیزی می‌گردید؟ |
| آیا این ایده خوب است؟ | الان این مشکل را چطور حل می‌کنید؟ |
| آیا حاضرید برای این هزینه کنید؟ | چقدر تا الان برای حل این مشکل هزینه/زمان صرف کرده‌اید؟ |

### جدول قانون برای Agent
| بررسی خودکار قبل از پرسیدن سؤال | اقدام |
|---|---|
| سؤال با «آیا فکر می‌کنید/دوست دارید» شروع می‌شود | بازنویسی به فرم رفتاری |
| سؤال شامل فرض ضمنی دربارهٔ ابزار/فرایند است | باز کردن سؤال به حالت خنثی |
| سؤال شامل عبارت هدایت‌کننده است | حذف عبارت، خنثی‌سازی لحن |
| پاسخ کاربر کلی/انتزاعی بود | فوراً سؤال پیگیری «مثال بزن / آخرین‌بار کِی بود؟» |

## ۳. چگونه از مشتری نیاز واقعی استخراج کنیم؟

### چرا نیاز واقعی به‌سادگی بیان نمی‌شود
مشتری معمولاً به‌جای نیاز واقعی، **ایدهٔ راه‌حل** یا **درخواست قابلیت (Feature Request)** ارائه می‌دهد. دلیل: او به مسئلهٔ ریشه‌ای دسترسی ذهنی مستقیم ندارد یا آنقدر از آن فاصله گرفته که فراموشش کرده.

### تکنیک‌های استخراج نیاز واقعی
1. **پرسیدن دربارهٔ گردش‌کار فعلی (Current Workaround):** «الان این کار را چطور انجام می‌دهید؟» — نشان می‌دهد آیا واقعاً به دنبال راه‌حل هستند یا صرفاً کنجکاوند.
2. **کاوش هزینهٔ فعلی مشکل:** چقدر زمان/پول/انرژی صرف این مشکل شده؟ (سنجهٔ شدت درد)
3. **زنجیرهٔ پیگیری (Five Whys):** با هر «چرا» یک لایه عمیق‌تر می‌روی تا از سطح قابلیت درخواستی به سطح انگیزهٔ واقعی برسی (جزئیات در بخش ۴).
4. **پرسیدن دربارهٔ آخرین تلاش برای حل مشکل:** آیا قبلاً امتحان کرده‌اند؟ چرا شکست خورده؟

### جدول قانون برای Agent
| علامت | تفسیر | اقدام |
|---|---|---|
| کاربر مستقیماً درخواست یک قابلیت مشخص می‌دهد | این احتمالاً راه‌حل پیشنهادی خودِ کاربر است، نه نیاز ریشه‌ای | فعال‌سازی فرآیند Feature→Problem (بخش ۴) |
| کاربر می‌گوید «الان دستی/با اکسل انجام می‌دهیم» | نشانهٔ وجود مشکل واقعی و هزینهٔ ملموس | ادامهٔ کاوش دربارهٔ میزان دردسر این روش |
| کاربر نمی‌تواند مثال مشخص از دفعهٔ اخیر بزند | ممکن است مشکل به‌اندازهٔ کافی واقعی/فوری نباشد | ثبت به‌عنوان «درد کم‌شدت»، ادامه به سراغ موضوع بعد |

## ۴. چگونه Feature را به Problem تبدیل کنیم؟

### چارچوب Five Whys
وقتی مشتری می‌گوید «یک دکمهٔ X می‌خواهم» یا «باید فلان قابلیت اضافه شود»، این نقطهٔ شروع است نه پایان. باید با پرسیدن مکرر «چرا این را می‌خواهید؟» (نه لزوماً دقیقاً ۵ بار، بلکه تا رسیدن به یک انگیزهٔ ریشه‌ای پایدار) از سطح راه‌حل به سطح مشکل رسید.

مثال زنجیره:
> «می‌خواهم چت آنلاین روی سایت باشد.» → چرا؟ → «چون مشتری‌ها زود ایمیل می‌فرستند و منتظر جواب می‌مانند.» → چرا این مشکل است؟ → «چون بعضی‌ها صبر نمی‌کنند و می‌روند سراغ رقیب.» → ریشه: **مشتریان بالقوه به‌خاطر تأخیر در پاسخ‌گویی از دست می‌روند** (نه لزوماً چت آنلاین راه‌حل باشد؛ می‌تواند FAQ قوی‌تر یا فرم تماس سریع‌تر هم باشد).

### چارچوب مکمل: Jobs To Be Done (JTBD)
به‌جای تمرکز روی محصول/قابلیت، بپرس مشتری با این وب‌سایت می‌خواهد چه «شغلی» (Job) را در زندگی/کسب‌وکارش انجام دهد. سؤال کلیدی: «این سایت قرار است چه کاری را برای شما آسان‌تر/سریع‌تر/مطمئن‌تر کند؟» — نه «چه صفحاتی می‌خواهید».

### قانون عملی
هر درخواست قابلیت باید قبل از ثبت در نیازمندی‌های پروژه از این فیلتر عبور کند: **«این قابلیت راه‌حل پیشنهادیِ چه مشکلی است؟»** اگر پاسخ روشن نبود، هنوز به مرحلهٔ نیازمندی نرسیده‌ایم.

### جدول قانون برای Agent
| ورودی کاربر | اقدام Agent |
|---|---|
| درخواست مستقیم قابلیت («فرم تماس بگذارید»، «چت بگذارید») | بلافاصله بپرس: «این به چه دردی می‌خورد؟» یا «چرا این برایتان مهم است؟» |
| پاسخ به «چرا» هنوز سطحی/مبهم بود | یک لایهٔ دیگر «چرا» بپرس، حداکثر تا ۵ لایه یا رسیدن به یک نتیجهٔ تجاری/احساسی روشن |
| به یک انگیزهٔ ریشه‌ای پایدار رسیدیم (مثلاً «از دست دادن مشتری») | آن را به‌عنوان Problem واقعی ثبت کن، قابلیت اولیه را فقط به‌عنوان «راه‌حل پیشنهادی کاربر» نگه‌دار، نه نیازمندی نهایی |

## ۵. چگونه Fact و Hypothesis را از هم جدا کنیم؟

### اصل بنیادین
بزرگ‌ترین خطای مصاحبهٔ Discovery، **اشتباه گرفتن نظر (Opinion) با واقعیت (Fact)** است. سؤال‌هایی مثل «این ایده را دوست دارید؟» نظر تولید می‌کنند نه واقعیت — و مردم به‌ندرت طبق چیزی که می‌گویند عمل می‌کنند.

### سه‌لایهٔ اطلاعات در مصاحبه (مدل هرم مشاهده → تفسیر → فرصت)
1. **Observation (مشاهده/واقعیت خام):** دقیقاً چه گفته/چه کاری کرده — بدون تفسیر.
2. **Interpretation (تفسیر):** آنچه مصاحبه‌گر از این مشاهده برداشت می‌کند — این جایی است که Hypothesis وارد می‌شود.
3. **Opportunity (فرصت/نیازمندی):** نتیجه‌گیری برای اقدام — که باید فقط بعد از تأیید کافی از لایهٔ ۱ ساخته شود، نه مستقیم از حدس.

### قانون تفکیک عملی برای هر جملهٔ مشتری
| نوع جمله | نشانه | برچسب |
|---|---|---|
| توصیف رفتار گذشتهٔ مشخص («هفتهٔ پیش این کار را با اکسل انجام دادم») | زمان/رویداد مشخص، قابل بررسی | **FACT** |
| بیان ترجیح یا نظر کلی («فکر می‌کنم بد است / خوب می‌شود») | فعل ذهنی، بدون ارجاع به رویداد | **OPINION** |
| پیش‌بینی رفتار آینده («اگر باشد حتماً استفاده می‌کنم») | زمان آینده + فرضی | **HYPOTHESIS (رد نشده یا تأیید نشده)** |
| تعریف/تمجید کلی («ایدهٔ خوبی است!») | بدون محتوای عملیاتی | **COMPLIMENT — نادیده گرفته شود** |

### هشدار Bias در تفسیر Agent
Confirmation Bias یعنی وقتی مصاحبه‌گر بین چند نکتهٔ گفته‌شده، فقط نکته‌ای را برجسته می‌کند که با فرضیهٔ اولیه‌اش هم‌خوان است. مصاحبه‌گر (چه انسان چه AI) باید هر بار بپرسد: «آیا من فقط داده‌ای که تأییدکنندهٔ فرض من است را انتخاب می‌کنم؟»

### جدول قانون برای Agent
| نوع پاسخ | برچسب خودکار | اقدام بعدی |
|---|---|---|
| شامل زمان/رویداد مشخص گذشته | FACT | ثبت به‌عنوان شاهد قابل‌استناد |
| شامل «فکر می‌کنم / احتمالاً / شاید استفاده کنم» | HYPOTHESIS | ثبت به‌عنوان فرضیهٔ تأییدنشده؛ در گزارش نهایی به‌روشنی از FACT جدا شود |
| فقط تعریف/تمجید بدون جزئیات | COMPLIMENT | نادیده گرفته شود؛ سؤال پیگیری برای رسیدن به FACT پرسیده شود |
| در تعارض با فرضیهٔ اولیهٔ Agent | — | باید با همان وزن FACTهای هم‌راستا ثبت شود؛ حذف یا کم‌اهمیت‌جلوه‌دادن ممنوع |

## ۶. سؤال‌های ضروری برای فهم هر بُعد

> همهٔ سؤال‌ها باید طبق اصول بخش ۲ (رفتاری، باز، بدون هدایت) پرسیده شوند. این بانک سؤال، پایهٔ اولیه برای Agent است و باید بر اساس پاسخ‌های قبلی پویا شخصی‌سازی شود.

### الف) Business (کسب‌وکار)
- کسب‌وکار شما دقیقاً چه کاری انجام می‌دهد و چطور درآمد کسب می‌کند؟
- الان مشتری‌ها را عمدتاً از چه مسیری پیدا می‌کنید؟
- شش ماه گذشته، بزرگ‌ترین چالش کسب‌وکارتان چه بود؟
- چه چیزی باعث می‌شود این کسب‌وکار را از رقبا متفاوت کند؟ (توضیح بده با یک مثال واقعی)

### ب) Customer (مشتری)
- مشتری فعلی شما دقیقاً چه کسی است؟ (نقش، صنعت، اندازه، ویژگی)
- آخرین مشتری‌ای که جذب کردید، چطور شما را پیدا کرد؟
- مشتری‌های خوب شما چه ویژگی مشترکی دارند؟
- چه نوع مشتری‌ای معمولاً شما را ترک می‌کند یا مناسب شما نیست؟ چرا؟

### پ) Problem (مشکل)
- الان بدون این وب‌سایت جدید، این کار را چطور انجام می‌دهید؟
- آخرین‌باری که نبودِ سایت خوب برایتان مشکل ایجاد کرد، چه اتفاقی افتاد؟
- این مشکل چقدر مکرر پیش می‌آید؟
- تا الان چقدر وقت/هزینه صرف حل این مشکل کرده‌اید؟

### ت) Goal (هدف)
- موفقیت این پروژه در سه ماه بعد از راه‌اندازی برای شما دقیقاً چه شکلی است؟
- اگر فقط یک نتیجهٔ مشخص از این سایت به‌دست بیاید، آن نتیجه چیست؟
- این هدف را با چه عددی می‌سنجید؟ (تعداد لید، فروش، زمان صرفه‌جویی‌شده)

### ث) Motivation (انگیزه)
- چرا الان (نه شش ماه پیش، نه شش ماه بعد) تصمیم به این پروژه گرفتید؟
- چه اتفاقی افتاد که این تصمیم را جدی کرد؟
- اگر این پروژه انجام نشود، چه چیزی از دست می‌رود؟

### ج) User (کاربر نهایی سایت)
- کاربر واقعی این سایت روزمره چه کارهایی انجام می‌دهد؟ سطح آشنایی‌اش با تکنولوژی چطور است؟
- کاربر از چه دستگاهی بیشتر استفاده می‌کند؟ (بر اساس داده، نه حدس)
- چه چیزی معمولاً کاربران شما را از انجام یک اقدام روی سایت (خرید، تماس، ثبت‌نام) منصرف می‌کند؟

### چ) Trust (اعتماد)
- مشتری‌های شما قبل از تصمیم‌گیری، چه چیزی را بررسی می‌کنند؟
- تا حالا مشتری‌ای بوده که به‌خاطر بی‌اعتمادی به سایت یا برند شما منصرف شود؟ چه چیزی باعث آن شد؟
- الان چه مدرکی (نمونه‌کار، گواهی، نظر مشتری) دارید که به‌کارگیری‌اش را در سایت در نظر نگرفته‌اید؟

### ح) Competition (رقابت)
- الان مشتری‌های شما به چه گزینه‌های دیگری (نه لزوماً رقیب مستقیم) فکر می‌کنند؟
- سه رقیبی که واقعاً نگرانشان هستید کدام‌اند؟ چرا آن‌ها؟
- آخرین‌باری که یک مشتری بین شما و یک رقیب مردد بود چه شد و چرا؟

### جدول اولویت‌بندی برای Agent
| بُعد | زمان مناسب در فلوی مصاحبه | وابستگی |
|---|---|---|
| Business | ابتدای مصاحبه (زمینه‌سازی) | — |
| Customer | بلافاصله بعد از Business | Business |
| Problem | بعد از Customer (مهم‌ترین بخش) | Customer |
| Goal | بعد از Problem | Problem |
| Motivation | همزمان یا بلافاصله بعد از Goal | Goal |
| User | موازی با Customer، عمیق‌تر | Customer |
| Trust | نزدیک انتهای مصاحبه | Problem, Competition |
| Competition | نزدیک انتها، قبل از جمع‌بندی | Business, Customer |

## ۷. اشتباهات رایج مصاحبه

| اشتباه | چرا مضر است | راه اصلاح |
|---|---|---|
| **معرفی زودهنگام ایده/راه‌حل** | مکالمه را «آلوده» می‌کند؛ پاسخ‌ها واکنش به پیچ می‌شوند نه واقعیت زندگی مشتری | تا رسیدن به مرحلهٔ مشخص در فلو، از راه‌حل صحبت نکن |
| **سؤال فرضی/آینده‌نگر** («آیا استفاده می‌کنید؟») | تولید نیت (Intention) نه رفتار (Behavior)؛ نیت‌ها پیش‌بینی ضعیفی از عمل واقعی‌اند | تبدیل به سؤال دربارهٔ گذشتهٔ مشخص (Last Time Test) |
| **سؤال هدایت‌کننده (Leading Question)** («مگر نه که سایت شلوغ است؟») | پاسخ را از قبل در خود دارد و نظر واقعی را می‌پوشاند | حذف عبارات هدایت‌کننده، طرح سؤال خنثی |
| **قبول تعریف/تمجید به‌عنوان داده** («ایدهٔ خوبیه!») | تعریف اطلاعات عملیاتی صفر دارد و اغلب صرفاً ادب اجتماعی است | نادیده گرفتن، پیگیری با «چرا فکر می‌کنید خوب است؟ چه چیزی الان این مشکل را دارد؟» |
| **حرف زدن بیشتر از گوش‌دادن** | مصاحبه‌گر جای پاسخ کاربر را با توضیح خودش پر می‌کند | نسبت حرف‌زدن Agent باید کم و پرسش‌محور بماند |
| **Confirmation Bias** (توجه انتخابی به داده‌های هم‌راستا با فرض اولیه) | نتیجه‌گیری اشتباه، نادیده‌گرفتن سیگنال‌های مخالف | هر پاسخ مخالفِ فرضیه باید با همان وزن ثبت شود، نه کم‌رنگ یا حذف |
| **Anchoring (لنگراندازی بر اولین پاسخ)** | پاسخ‌های بعدی بر اساس تأثیر اولین پاسخ تفسیر می‌شوند | هر پاسخ باید مستقل از پاسخ‌های قبلی ارزیابی شود |
| **نادیده گرفتن داده‌های پرت (Outliers)** | یک پاسخ ناهمسو ممکن است مهم‌ترین سیگنال باشد، نه نویز | داده‌های پرت را ثبت و علامت‌گذاری کن، حذف نکن |
| **فرض‌سازی در خودِ سؤال** («چطور سیستم X را با Y یکپارچه می‌کنید؟» وقتی معلوم نیست هر دو را دارند) | اگر فرض غلط باشد، کل مسیر مصاحبه منحرف می‌شود | همیشه با سؤال بازتر و خنثی شروع کن، بعد دقیق‌تر شو |
| **رسمی/بیش‌ازحد فرم‌گونه‌کردن مکالمه** | جو غیرطبیعی باعث پاسخ‌های سطحی/محتاطانه می‌شود | لحن مکالمه‌ای، نه بازجویی؛ پیگیری طبیعی به‌جای پرش مکانیکی بین سؤال‌ها |

## خلاصهٔ منطق مصاحبهٔ AI Agent (State Machine پیشنهادی)

### مراحل فلو
1. **Opening:** معرفی کوتاه، توضیح که هدف فهمیدن وضعیت واقعی است نه پیشنهاد راه‌حل.
2. **Business Context:** سؤال‌های بخش الف.
3. **Customer & User:** سؤال‌های بخش ب و ج به‌صورت موازی.
4. **Problem Deep-Dive:** سؤال‌های بخش پ + فعال‌سازی Five Whys برای هر Feature Request که کاربر مطرح می‌کند.
5. **Goal & Motivation:** سؤال‌های بخش ت و ث.
6. **Trust & Competition:** سؤال‌های بخش چ و ح.
7. **Wrap-up & Validation:** خلاصه‌سازی آنچه فهمیده شده و تأیید گرفتن از کاربر («درست فهمیدم که...؟») — این خودش یک سنجهٔ Fact-Check است.

### قوانین کلی حاکم بر کل فلو (اعمال در هر مرحله)
| قانون | توضیح |
|---|---|
| Feature Trap Detector | هر بار کاربر یک قابلیت مشخص درخواست کرد → فعال‌سازی خودکار Five Whys پیش از ثبت آن به‌عنوان نیاز |
| Fact/Hypothesis Tagger | هر پاسخ کاربر باید قبل از ذخیره با یکی از برچسب‌های FACT / HYPOTHESIS / OPINION / COMPLIMENT علامت‌گذاری شود |
| Last Time Test Filter | هر سؤال Agent پیش از پرسیده‌شدن باید از فیلتر «آیا قابل تبدیل به فرم گذشته/رفتاری هست؟» عبور کند |
| Compliment Ignorer | جملات تعریف/تمجید بدون محتوای عملیاتی وارد گزارش نهایی نمی‌شوند؛ فقط سؤال پیگیری تولید می‌کنند |
| No-Pitch Rule | تا پایان فاز Problem Deep-Dive، Agent هیچ پیشنهاد راه‌حل/ویژگی مطرح نمی‌کند |
| Outlier Preserver | پاسخ‌های ناهمسو با روند غالب باید در گزارش نهایی با برچسب «نیازمند بررسی بیشتر» حفظ شوند، نه حذف |
| Follow-up Trigger | هر پاسخ کوتاه‌تر از یک آستانه یا فاقد جزئیات زمانی/رویدادی، به‌طور خودکار یک سؤال پیگیری تولید می‌کند |
