# چارچوب ارزیابی قابلیت (Feature Evaluation Framework)
### سند مرجع برای تشخیص خودکار «چه چیزی باید ساخته شود» وقتی مشتری می‌گوید «این قابلیت را می‌خواهم»

مدل هسته: `Feature → Problem → User → Impact → Alternative Solution → Decision`

---

## نحوه استفاده از این سند توسط Agent

این سند برای لحظه‌ای طراحی شده که مشتری یک **قابلیت مشخص** درخواست می‌دهد (نه یک مشکل). وظیفهٔ Agent عبور این درخواست از شش ایستگاه، پیش از تبدیل آن به Requirement (طبق سند «مهندسی نیازمندی») است. این سند مکمل بخش ۴ سند Requirement Engineering است (تبدیل Feature به Problem)؛ اینجا آن فرآیند به‌طور کامل و با مثال‌های واقعی برای هفت قابلیت رایج وب‌سایت باز شده.

### چرا این مدل لازم است
اکثر قابلیت‌های اضافه‌شده به یک محصول نه از سر بدخواهی بلکه از سر ایده‌های خوبِ به‌موقع‌نیامده به سیستم راه پیدا می‌کنند. راه مقابله، نه رد کردن همهٔ درخواست‌ها بلکه **عبور اجباری هر درخواست از یک فیلتر ساختاریافته** است — نه بر اساس سلیقه یا فشار ذی‌نفع، بلکه بر اساس شواهد.

---

## مرحله ۱: Feature (قابلیت درخواستی)

### تعریف
همان چیزی که مشتری به‌صراحت گفته — یک اسم/راه‌حل مشخص («چت‌بات می‌خواهم»، «سرچ بگذارید»). این نقطهٔ **شروع** بررسی است، نه پایان.

### قانون برای Agent
| قاعده | توضیح |
|---|---|
| هرگز مستقیم Feature را ثبت/تأیید نکن | باید ابتدا از پنج ایستگاه بعدی عبور کند |
| عین جملهٔ مشتری را بدون تفسیر ذخیره کن | برای حفظ ردیابی‌پذیری با سند مصاحبه |
| بررسی کن آیا این یک درخواست تکراری/پرتکرار از چند مشتری است یا صرفاً خواستهٔ یک نفر | طبق اصل «تصمیم بر اساس روند، نه یک صدا»، درخواست‌های فردی وزن کمتری نسبت به الگوهای پرتکرار دارند |

---

## مرحله ۲: Problem (تبدیل Feature به مشکل ریشه‌ای)

### تعریف
همان تکنیک Five Whys که در سند مصاحبه توضیح داده شد: با پرسیدن مکرر «این برای چه دردی است؟» از سطح راه‌حل به سطح مشکل واقعی می‌رسیم.

### سؤال کلیدی Agent
> «اگر این قابلیت وجود نداشت، دقیقاً چه اتفاق بدی می‌افتاد؟»

اگر پاسخ این سؤال روشن و ملموس نبود، یعنی هنوز به Problem واقعی نرسیده‌ایم و ادامهٔ مسیر (Impact، Decision) بی‌معناست.

### قانون برای Agent
| علامت پاسخ | تفسیر |
|---|---|
| پاسخ شامل یک پیامد کسب‌وکاری/کاربری مشخص است («مشتری می‌رود سراغ رقیب») | Problem واقعی شناسایی شد → ادامهٔ مسیر |
| پاسخ فقط تکرار همان Feature است («چون خب لازم است») | هنوز Problem پیدا نشده → یک لایهٔ دیگر «چرا» بپرس |
| پاسخ صرفاً یک ترند/رقیب است («چون رقبا دارند») | نشانهٔ ضعیف؛ باید جدا بررسی شود آیا مشتریانِ خودِ ما هم همین مشکل را دارند |

---

## مرحله ۳: User (چه کسی واقعاً درگیر این مشکل است؟)

### تعریف
باید مشخص شود این مشکل برای **چه بخشی از کاربران واقعی**، با چه فراوانی، رخ می‌دهد — نه یک فرض کلی دربارهٔ «کاربران».

### سؤال‌های کلیدی
- این مشکل برای چند درصد از کاربران/بازدیدکنندگان واقعی رخ می‌دهد؟
- آیا این مشکل مخصوص یک سگمنت خاص (مثلاً فقط کاربران موبایل، فقط مشتریان سازمانی) است یا عمومی؟
- آیا داده‌ای (آنالیتیکس، تیکت پشتیبانی، مصاحبه) برای اثبات این وجود دارد یا فقط حدس است؟

### قانون برای Agent
| شرط | اقدام |
|---|---|
| مشکل برای بخش بزرگی از کاربران هدف اصلی رخ می‌دهد | ادامه به Impact با وزن بالا |
| مشکل فقط برای یک نفر/یک Edge Case خاص است | وزن پایین؛ به سمت Nice-to-have یا Don't Build (طبق قانون «تصمیم بر اساس روند، نه صدای فردی») |
| هیچ داده‌ای برای اثبات فراوانی وجود ندارد | این را به‌عنوان HYPOTHESIS ثبت کن و پیشنهاد بده قبل از ساخت، اعتبارسنجی سبک (مثلاً نظرسنجی کوچک) انجام شود |

---

## مرحله ۴: Impact (این قابلیت چقدر واقعاً روی هدف اثر می‌گذارد؟)

### چارچوب سنجش (اقتباسی سبک از RICE)
برای هر Feature سه بعد را بدون فرمول پیچیده امتیازدهی کن:
- **Reach (دامنه):** این قابلیت روی چند نفر/چه سهمی از کاربران اثر می‌گذارد؟
- **Impact (شدت اثر):** اگر ساخته شود، چقدر روی هدف اصلی سایت (تبدیل، رضایت، کاهش هزینهٔ پشتیبانی) اثر دارد؟
- **Confidence (اطمینان):** چقدر مطمئنیم این تخمین درست است؟ (داده واقعی دارد یا فقط حدس تیم است؟)

فرمول ساده برای رتبه‌بندی نسبی: `امتیاز = (Reach × Impact × Confidence) / Effort` — Effort در مرحلهٔ بعد (Alternative/Decision) از تیم فنی گرفته می‌شود.

### قانون برای Agent
| شرط | تفسیر امتیاز |
|---|---|
| Reach بالا + Impact بالا + Confidence بالا (داده واقعی) | کاندید قوی برای Must/Should Have |
| Reach پایین + Impact پایین، هر Confidence | کاندید Nice-to-have یا Don't Build |
| Impact بالا ولی Confidence پایین (فقط حدس) | قبل از تصمیم قطعی، اعتبارسنجی سبک پیشنهاد شود (مثلاً MVP کوچک یا تست A/B) نه ساخت کامل |

---

## مرحله ۵: Alternative Solution (آیا راه‌حل ارزان‌تر/ساده‌تری هم برای همین Problem هست؟)

### اصل کلیدی
مشتری معمولاً یک **راه‌حل** را با نام قابلیت بیان می‌کند، نه لزوماً بهترین راه‌حل. وظیفهٔ Agent این است که پیش از تأیید ساخت آن قابلیت، حداقل یک یا دو جایگزین ارزان‌تر/سریع‌تر را کنار آن بگذارد.

### دسته‌های رایج جایگزین
- **راه‌حل محتوایی به‌جای فنی:** آیا یک صفحهٔ FAQ خوب، مشکل را حل می‌کند به‌جای ساخت چت‌بات؟
- **راه‌حل دستی/فرآیندی به‌جای اتوماسیون:** آیا در مرحلهٔ فعلی (کم‌ترافیک) یک فرآیند دستی کافی است تا نیاز واقعی اثبات شود؟
- **ابزار آماده (Buy) به‌جای ساخت اختصاصی (Build):** آیا یک سرویس آماده (مثل ویجت چت آماده، سیستم رزرو SaaS) سریع‌تر و ارزان‌تر از توسعهٔ اختصاصی است؟
- **بهبود چیزی که از قبل هست:** آیا مشکل با اصلاح ساختار/UX فعلی (بدون قابلیت جدید) حل می‌شود؟

### قانون برای Agent
| شرط | اقدام |
|---|---|
| جایگزین ارزان‌تر با همان اثر پیدا شد | جایگزین را به‌عنوان گزینهٔ اول به تصمیم‌گیرنده پیشنهاد بده |
| هیچ جایگزین معقولی برای این سطح از Impact پیدا نشد | Feature اصلی وارد مرحلهٔ Decision شود |
| جایگزین «ابزار آماده» موجود است ولی محدودیت دارد (برندینگ، یکپارچگی) | هر دو گزینه (Buy vs Build) با مزایا/معایب به تصمیم‌گیرنده ارائه شود |

---

## مرحله ۶: Decision (تصمیم نهایی)

### چهار خروجی ممکن
| تصمیم | شرط |
|---|---|
| **Build (بساز)** | Problem واقعی + User با دامنهٔ کافی + Impact بالا + Confidence کافی + بدون جایگزین ارزان‌تر مناسب |
| **Buy/Adapt (بخر یا از ابزار موجود استفاده کن)** | Problem واقعی هست، اما یک ابزار آماده با هزینهٔ کمتر همان اثر را می‌دهد |
| **Simplify (نسخهٔ ساده‌تر بساز)** | Problem واقعی هست ولی Impact/Confidence برای نسخهٔ کامل کافی نیست؛ یک نسخهٔ کوچک برای اعتبارسنجی کافی است |
| **Don't Build (نساز)** | Problem مبهم/غیرواقعی است، یا User محدود به یک مورد خاص است، یا Impact/Confidence خیلی پایین است |

هر تصمیم باید به سند «مهندسی نیازمندی» (Requirement Engineering) با اولویت مربوطه (Must/Should/Nice-to-have/Don't Build) وصل شود.

## کاربرد مدل روی ۷ قابلیت رایج وب‌سایت

> این جدول‌ها **نمونه‌های راهنما** هستند، نه حکم قطعی — تصمیم نهایی همیشه باید بر اساس داده‌های واقعی همان پروژه گرفته شود. هدف نشان دادن **نوع سؤالی است که باید پرسیده شود**.

### ۱. Chatbot (چت‌بات)
| مرحله | تحلیل نمونه |
|---|---|
| Feature | «می‌خواهم چت‌بات روی سایت باشد» |
| Problem | معمولاً ریشه: پاسخ‌گویی کند به سؤالات پرتکرار، از دست رفتن لید در ساعات غیرکاری |
| User | بازدیدکنندگانی که سؤال قبل از خرید/تماس دارند — باید بررسی شود چند درصدند |
| Impact | اگر حجم سؤالات پرتکرار بالا و پاسخ‌گویی واقعاً کند است، Impact بالا؛ اگر تعداد سؤالات کم است، Impact پایین |
| Alternative | صفحهٔ FAQ قوی + فرم تماس سریع‌تر + اعلام ساعت پاسخ‌گویی؛ یا ویجت چت آمادهٔ ارزان (Buy) به‌جای چت‌بات هوشمند اختصاصی |
| Decision نمونه | اگر حجم پایین: **Don't Build** (فعلاً FAQ کافی است) | اگر حجم بالا و تکراری: **Buy/Adapt** (ویجت چت آماده) | اگر نیاز به پاسخ اختصاصی/داده‌محور دارد: **Build** |

### ۲. Search (جستجوی سایت)
| مرحله | تحلیل نمونه |
|---|---|
| Feature | «باید سرچ روی سایت باشد» |
| Problem | کاربر در حجم زیاد محتوا/محصول گم می‌شود و پیدا نمی‌کند |
| User | مرتبط با سایت‌هایی با تعداد صفحه/محصول/مقالهٔ زیاد (مثلاً بیش از ۲۰-۳۰ آیتم)؛ در سایت‌های کوچک اغلب غیرضروری |
| Impact | اگر تعداد صفحات کم است (مثلاً سایت خدماتی با ۵-۶ صفحه)، Impact پایین؛ اگر فروشگاه/بلاگ بزرگ است، Impact بالا |
| Alternative | ناوبری و دسته‌بندی بهتر (Information Architecture) به‌جای سرچ، در سایت‌های کوچک |
| Decision نمونه | سایت کوچک با تعداد صفحهٔ محدود: **Don't Build** (بهبود ناوبری کافی است) | فروشگاه/آرشیو بزرگ: **Build** یا **Buy** (پلاگین سرچ آماده) |

### ۳. Animation (انیمیشن/جلوه‌های حرکتی)
| مرحله | تحلیل نمونه |
|---|---|
| Feature | «می‌خواهم سایت انیمیشن‌های شیک داشته باشد» |
| Problem | معمولاً ریشهٔ واقعی «حرفه‌ای/مدرن به‌نظر برسیم» است — باید بررسی شود آیا واقعاً مشکل اعتماد/برند هست یا صرفاً سلیقه |
| User | همهٔ بازدیدکنندگان تحت تأثیر قرار می‌گیرند، اما جهت اثر (مثبت/منفی) به کیفیت اجرا و سرعت بارگذاری بستگی دارد |
| Impact | ریسک بالا: انیمیشن سنگین می‌تواند سرعت صفحه و تجربهٔ موبایل را خراب کند و اثر معکوس روی تبدیل بگذارد |
| Alternative | انیمیشن‌های ظریف و سبک (Micro-interactions) به‌جای جلوه‌های سنگین؛ یا تمرکز روی تایپوگرافی/عکاسی حرفه‌ای برای حس مدرن‌بودن |
| Decision نمونه | اگر هدف صرفاً زیبایی سلیقه‌ای بدون ارتباط به Problem مشتری واقعی است: **Simplify** (نسخهٔ سبک) یا **Don't Build** اگر ریسک سرعت بالا باشد |

### ۴. Login (سیستم ورود/عضویت کاربر)
| مرحله | تحلیل نمونه |
|---|---|
| Feature | «کاربران باید بتوانند لاگین کنند» |
| Problem | باید مشخص شود چرا: پیگیری سفارش؟ محتوای اختصاصی؟ اشتراک؟ بدون Problem مشخص، Login صرفاً اصطکاک اضافه به کاربر تحمیل می‌کند |
| User | فقط کاربرانی که نیاز به دسترسی مکرر/شخصی‌سازی‌شده دارند؛ برای بازدیدکنندهٔ یک‌باره بی‌فایده و حتی مانع تبدیل است |
| Impact | ریسک بالا برای وب‌سایت‌های Service/Portfolio: افزودن Login بدون نیاز واقعی می‌تواند نرخ تبدیل را کاهش دهد (اصطکاک اضافه) |
| Alternative | Checkout/فرم بدون نیاز به عضویت (Guest Flow)؛ یا لینک‌های امن یک‌بارمصرف به‌جای حساب کاربری کامل |
| Decision نمونه | اگر Problem واقعی (مثل پنل مشتری برای پیگیری پروژه) اثبات شد: **Build** | اگر فقط «رایج است پس بگذاریم»: **Don't Build** |

### ۵. Dashboard (پنل کاربری/داشبورد)
| مرحله | تحلیل نمونه |
|---|---|
| Feature | «مشتری‌ها باید داشبورد شخصی داشته باشند» |
| Problem | معمولاً ریشه: نیاز به دیدن وضعیت سفارش/پروژه/مصرف بدون تماس مکرر با پشتیبانی |
| User | کاربرانی با تعامل مکرر و طولانی‌مدت (نه بازدیدکنندهٔ یک‌بار)؛ باید فراوانی نیاز به بازگشت به سایت سنجیده شود |
| Impact | اگر تعداد کاربران بازگشتی کم است، هزینهٔ ساخت/نگهداری داشبورد نسبت به ارزش آن بالا می‌شود |
| Alternative | ایمیل‌های خودکار وضعیت (Status Update) به‌جای پنل کامل؛ یا استفاده از ابزار آمادهٔ CRM/Portal (Buy) |
| Decision نمونه | تعامل مکرر و پیچیده اثبات‌شده: **Build** | تعامل کم یا ساده: **Simplify** (ایمیل خودکار) یا **Don't Build** |

### ۶. AI Features (قابلیت‌های هوش مصنوعی روی سایت)
| مرحله | تحلیل نمونه |
|---|---|
| Feature | «می‌خواهیم از AI روی سایت استفاده کنیم» (اغلب مبهم‌ترین درخواست) |
| Problem | این درخواست اغلب از جنس «ترند» است نه Problem مشخص؛ باید با Five Whys به یک نیاز عینی (مثلاً «کاهش زمان پاسخ»، «شخصی‌سازی توصیه») رسید |
| User | تا Problem مشخص نشود، User هم قابل تعریف نیست |
| Impact | بدون Problem و User مشخص، Impact قابل سنجش نیست — این نشانهٔ کلاسیک HYPOTHESIS بدون FACT است |
| Alternative | معمولاً یک راه‌حل غیر-AI ساده‌تر (بهبود محتوا، فیلتر ساده، فرم هوشمند بدون مدل AI) همان مشکل را حل می‌کند |
| Decision نمونه | اگر پس از Five Whys به Problem مشخص با داده نرسیدیم: **Don't Build** (بازگشت به Discovery) | اگر Problem مشخص شد (مثلاً حجم بالای سؤالات تکراری): آن‌گاه به قابلیت مشخص‌تر (مثلاً Chatbot) تبدیل شود و از ابتدای فرآیم دوباره ارزیابی شود |

### ۷. Booking (سیستم رزرو/نوبت‌دهی)
| مرحله | تحلیل نمونه |
|---|---|
| Feature | «سیستم رزرو آنلاین می‌خواهیم» |
| Problem | ریشه معمولاً: هماهنگی تلفنی/دستی وقت زمان‌بر است و باعث از دست رفتن مشتری یا خطای زمان‌بندی می‌شود |
| User | مشتریانی که نیاز به تعیین وقت/جلسه/خدمت زمان‌دار دارند (کسب‌وکارهای خدماتی، کلینیک، مشاوره) |
| Impact | در کسب‌وکارهای با حجم بالای هماهنگی دستی، Impact بسیار بالاست (کاهش مستقیم هزینهٔ عملیاتی + کاهش نرخ ازدست‌رفتن مشتری) |
| Alternative | ابزار رزرو آمادهٔ SaaS (Calendly و مشابه) به‌جای توسعهٔ اختصاصی، مگر نیاز به قوانین پیچیدهٔ اختصاصی (مثل رزرو گروهی، منابع محدود) باشد |
| Decision نمونه | نیاز ساده و استاندارد: **Buy/Adapt** | نیاز با قوانین پیچیدهٔ اختصاصی کسب‌وکار: **Build** |

### جدول جمع‌بندی سریع برای Agent
| قابلیت | ریسک رایج اگر بدون بررسی ساخته شود |
|---|---|
| Chatbot | هزینهٔ نگهداری بالا برای حجم پایین سؤال |
| Search | پیچیدگی اضافه برای سایتی که اصلاً محتوای زیاد ندارد |
| Animation | افت سرعت/تجربهٔ موبایل، اثر معکوس روی تبدیل |
| Login | اصطکاک اضافه، افت نرخ تبدیل بدون نیاز واقعی |
| Dashboard | هزینهٔ ساخت/نگهداری بالا برای کاربرانی که به‌ندرت برمی‌گردند |
| AI Features | ساخت راه‌حلی برای مشکلی که هنوز تعریف نشده (پرهزینه‌ترین نوع اشتباه) |
| Booking | پیچیدگی و هزینهٔ اختصاصی‌سازی بی‌مورد وقتی ابزار آماده کافی بود |

## خروجی نهایی برای هر Feature (قالب ثبت تصمیم)

```
Feature: [نام قابلیت به زبان مشتری]
Problem (بعد از Five Whys): ...
User: [چه سگمنتی، چه درصدی، بر چه اساس داده‌ای]
Impact: Reach=[کم/متوسط/زیاد] Impact=[کم/متوسط/زیاد] Confidence=[کم/متوسط/زیاد]
Alternative Solutions بررسی‌شده: [لیست + چرا رد/قبول شدند]
Decision: Build / Buy-Adapt / Simplify / Don't Build
دلیل تصمیم: ...
اتصال به Requirement: [REQ-ID مرتبط طبق سند Requirement Engineering، اگر تصمیم Build/Buy/Simplify باشد]
```

### جدول قوانین نهایی تصمیم‌گیری خودکار برای Agent
| شرط ترکیبی | تصمیم پیش‌فرض |
|---|---|
| Problem مشخص + User با دامنهٔ بالا + Impact بالا + Confidence بالا + بدون جایگزین مناسب | Build |
| Problem مشخص + Impact متوسط/بالا + ابزار آماده با هزینهٔ کمتر موجود است | Buy/Adapt |
| Problem مشخص ولی Confidence پایین (فقط حدس) | Simplify (نسخهٔ کوچک برای اعتبارسنجی) |
| Problem مبهم پس از Five Whys، یا User محدود به یک مورد، یا Impact/Reach پایین | Don't Build |
| درخواست فقط برگرفته از ترند/رقیب بدون FACT پشتیبان از مشتریان خودمان | Don't Build (تا اعتبارسنجی مجزا) |

*این سند بر اساس اصول جلوگیری از Feature Creep (ارزیابی هر قابلیت در برابر چشم‌انداز محصول و نیاز واقعی کاربر)، چارچوب اولویت‌بندی RICE/ICE (Reach, Impact, Confidence, Effort)، و تصمیم‌گیری Buy vs Build تدوین شده و مستقیماً به سند «مهندسی نیازمندی» متصل می‌شود تا هر تصمیم Build/Buy/Simplify به یک Requirement رسمی با اولویت مشخص تبدیل شود.*
