# Knowledge Base: آگاهی فناوری وب‌سایت (Website Technology Awareness)

> **نوع سند:** مرجع تصمیم‌گیری برای AI Agent متخصص استراتژی وب‌سایت
> **کاربرد:** جلوگیری از پیشنهاد فناوری نامتناسب/غیرواقعی در مرحلهٔ Requirement — مکمل اسناد «Website Types»، «Anatomy»، «Industry Patterns» و «Content Strategy»
> **جایگاه در زنجیرهٔ تصمیم‌گیری:**
> `Website Type + Industry + Content Volume/Complexity` → **`Technology Decision`** → معماری فنی نهایی
> **هشدار محوری:** این سند برای لایهٔ **استراتژی** است، نه پیاده‌سازی. Agent نباید نام محصول/فریمورک خاص (مثل «وردپرس» یا «شاپیفای») را به‌عنوان تصمیم نهایی قطعی اعلام کند، بلکه باید **دستهٔ فناوری** (Category) را بر اساس معیارهای این سند توصیه کند و انتخاب ابزار مشخص را به مرحلهٔ فنی/اجرایی پروژه واگذار کند، مگر آنکه کارفرما محدودیت یا ترجیح مشخصی اعلام کرده باشد.

## 1. پنج دستهٔ فناوری و زمان استفادهٔ آن‌ها

### 1.1 CMS سنتی (Traditional/Monolithic CMS)
**تعریف:** سیستمی که مدیریت محتوا (Backend) و نمایش آن (Frontend) در یک پلتفرم یکپارچه انجام می‌شود.

**چه زمانی مناسب است:**
- کسب‌وکار نیاز به به‌روزرسانی مکرر محتوا توسط افراد غیرفنی دارد (مثل بازاریابی، مدیر محتوا)
- ساختار سایت نسبتاً استاندارد است (Corporate، Blog، سایت خدماتی ساده) و نیاز به تعامل پیچیده یا داده‌محور ندارد
- بودجه و زمان توسعه محدود است و اکوسیستم آماده (قالب، افزونه) می‌تواند هزینه را کاهش دهد
- نیازی به مقیاس‌پذیری فوق‌العاده بالا یا تجربهٔ کاربری کاملاً سفارشی نیست

**چه زمانی نامناسب است:**
- نیاز به منطق تجاری پیچیده، محاسبات Real-time، یا تعامل کاربری غیراستاندارد وجود دارد
- سایت باید محتوای خود را به چند کانال/پلتفرم مختلف (اپ موبایل، دستگاه IoT، چند سایت با یک منبع محتوا) توزیع کند

### 1.2 Static Website (سایت استاتیک)
**تعریف:** صفحاتی که از پیش (در زمان Build) تولید می‌شوند و بدون پردازش سمت سرور در لحظهٔ درخواست، مستقیماً تحویل داده می‌شوند.

**چه زمانی مناسب است:**
- محتوای سایت به‌ندرت تغییر می‌کند (Landing Page، Portfolio ساده، سایت رویداد، مستندات نسخه‌ثابت)
- اولویت اول سرعت بارگذاری و امنیت بالا (سطح حمله بسیار کمتر از سیستم‌های داینامیک) است
- نیازی به تعامل کاربر با پایگاه‌داده یا حساب کاربری در لحظه نیست
- هزینهٔ میزبانی باید حداقلی باشد

**چه زمانی نامناسب است:**
- نیاز به شخصی‌سازی محتوا بر اساس کاربر، فرم‌های پیچیده، حساب کاربری، یا محتوای اشتراکی/تراکنشی وجود دارد
- فرکانس به‌روزرسانی محتوا بسیار بالاست و فرآیند Build/Deploy مکرر عملی نیست (بدون ابزار مناسب CI/CD)

### 1.3 Web Application (اپلیکیشن تحت وب سفارشی)
**تعریف:** نرم‌افزار سفارشی‌ساخته‌شده با منطق تجاری اختصاصی، معمولاً شامل Backend و Frontend مجزا و پایگاه‌دادهٔ ساختاریافته.

**چه زمانی مناسب است:**
- کسب‌وکار نیاز به فرآیند/منطق منحصربه‌فرد دارد که هیچ پلتفرم آماده‌ای پوشش نمی‌دهد (SaaS، Marketplace، ابزار داخلی سازمانی، سیستم رزرو پیچیده)
- نیاز به مقیاس‌پذیری بالا، عملکرد بلادرنگ (Real-time)، یا یکپارچگی عمیق با سیستم‌های دیگر (API، پایگاه‌داده اختصاصی) وجود دارد
- محصول نرم‌افزاری خودِ کسب‌وکار است (نه صرفاً ویترین معرفی کسب‌وکار)

**چه زمانی نامناسب است:**
- نیاز واقعی فقط نمایش محتوا یا فروش ساده است — در این حالت Web Application هزینه و زمان توسعه را بدون دلیل موجه چندبرابر می‌کند
- تیم فنی/بودجهٔ نگهداری بلندمدت برای پشتیبانی از یک سیستم سفارشی وجود ندارد

### 1.4 Headless CMS
**تعریف:** سیستم مدیریت محتوا که فقط محتوا را از طریق API ارائه می‌دهد و مسئولیت نمایش (Frontend) کاملاً جدا و سفارشی است.

**چه زمانی مناسب است:**
- محتوا باید هم‌زمان در چند پلتفرم/کانال نمایش داده شود (سایت، اپ موبایل، دستگاه‌های دیگر) از یک منبع واحد
- تیم فنی نیاز به آزادی کامل در انتخاب فناوری Frontend (برای عملکرد یا تجربهٔ کاربری سفارشی) دارد، اما همچنان می‌خواهد مدیریت محتوا برای افراد غیرفنی ساده باشد
- پروژه نیاز به مقیاس‌پذیری و عملکرد بالاتر از CMS سنتی دارد ولی به پیچیدگی کامل یک Web Application اختصاصی نیاز نیست

**چه زمانی نامناسب است:**
- تیم فنی یا بودجه برای ساخت و نگهداری Frontend جداگانه وجود ندارد (Headless CMS به‌تنهایی سایت نمایش نمی‌دهد و همیشه به توسعهٔ Frontend اضافی نیاز دارد)
- نیاز پروژه ساده و تک‌کاناله است؛ در این حالت پیچیدگی اضافه بدون بازده توجیه‌پذیر نیست

### 1.5 Ecommerce Platforms (پلتفرم‌های تخصصی فروشگاهی)
**تعریف:** سیستم‌های آماده یا نیمه‌آماده که زیرساخت فروش آنلاین (کاتالوگ، سبد خرید، پرداخت، موجودی) را از پیش فراهم می‌کنند.

**چه زمانی مناسب است:**
- کسب‌وکار محصول فیزیکی/دیجیتال استاندارد می‌فروشد و فرآیند فروش آن با الگوهای رایج Ecommerce (کاتالوگ → سبد → Checkout) همخوانی دارد
- نیاز به راه‌اندازی سریع و اتکا به ویژگی‌های آزموده‌شده (امنیت پرداخت، مدیریت مالیات، یکپارچگی با سیستم‌های ارسال) وجود دارد
- حجم و پیچیدگی فروش در محدودهٔ قابل پوشش توسط پلتفرم است (نه یک Marketplace چندفروشندهٔ بسیار پیچیده)

**چه زمانی نامناسب است:**
- مدل کسب‌وکار غیراستاندارد است (مثل Marketplace چندطرفه با تسویهٔ پیچیدهٔ مالی، یا قیمت‌گذاری کاملاً پویا/سفارشی) و پلتفرم آماده امکان پیاده‌سازی منطق موردنیاز را نمی‌دهد
- نیاز به یکپارچگی عمیق و اختصاصی با سیستم‌های داخلی کسب‌وکار (ERP سفارشی، انبارداری خاص) دارد که پلتفرم آماده محدودیت ایجاد می‌کند

## 2. جدول تصمیم سریع (Decision Matrix)

| معیار ورودی | CMS سنتی | Static | Web App | Headless CMS | Ecommerce Platform |
|---|---|---|---|---|---|
| فرکانس تغییر محتوا | متوسط-بالا | کم | متغیر (بستگی به منطق) | متوسط-بالا | متوسط |
| نیاز به چندکاناله‌بودن محتوا | خیر | خیر | بستگی به معماری | بله | خیر (معمولاً) |
| پیچیدگی منطق تجاری | کم-متوسط | خیلی کم | بالا | کم-متوسط (در محتوا) | متوسط (استاندارد فروش) |
| بودجه/زمان توسعه | محدود تا متوسط | خیلی محدود | بالا | متوسط تا بالا | محدود تا متوسط |
| نیاز به تیم فنی برای نگهداری مستمر | کم | خیلی کم | بالا | متوسط تا بالا | کم-متوسط |
| مدل کسب‌وکار استاندارد است؟ | بله | بله | معمولاً خیر (سفارشی) | بستگی دارد | بله |

## 3. تصمیم‌های فنی که باید در مرحلهٔ Strategy گرفته شوند

این تصمیمات باید **قبل از** ورود به مرحلهٔ طراحی بصری یا انتخاب ابزار مشخص اتخاذ شوند؛ در غیر این صورت، پروژه در میانهٔ راه با محدودیت‌های فنی غیرمنتظره مواجه می‌شود.

### 3.1 دستهٔ فناوری (Technology Category)
تعیین اینکه کدام یک از پنج دستهٔ بالا با «نوع سایت» (از سند Website Types)، «حجم/پیچیدگی محتوا» (از سند Content Strategy)، و «نیاز صنعتی» (از سند Industry Patterns) همخوانی دارد. این تصمیم پایه‌ای‌ترین خروجی مرحلهٔ Strategy است.

### 3.2 مالکیت و نگهداری محتوا (Content Ownership Model)
مشخص‌شدن اینکه چه کسی، با چه فرکانسی، و با چه سطح مهارت فنی محتوا را به‌روزرسانی می‌کند. این تصمیم مستقیماً روی انتخاب بین CMS/Headless CMS/Static اثر می‌گذارد؛ نادیده‌گرفتن آن رایج‌ترین علت شکست فنی پروژه‌هاست (مثلاً انتخاب سایت استاتیک برای کسب‌وکاری که روزانه محتوا اضافه می‌کند).

### 3.3 مقیاس‌پذیری موردانتظار (Scalability Requirement)
برآورد واقع‌بینانه (نه آرمانی) از ترافیک، حجم داده، و تعداد کاربران هم‌زمان در افق ۱ تا ۳ سال آینده. تصمیم فناوری باید متناسب با این برآورد باشد، نه بر اساس بلندپروازی فرضی («شاید میلیون‌ها کاربر داشته باشیم») که منجر به پیچیدگی و هزینهٔ غیرضروری اولیه می‌شود (Over-engineering).

### 3.4 نیاز به یکپارچگی با سیستم‌های دیگر (Integration Requirements)
شناسایی تمام سیستم‌های خارجی که سایت باید با آن‌ها ارتباط داشته باشد: درگاه پرداخت، CRM، ابزار ایمیل مارکتینگ، سیستم انبارداری/ERP، ابزار تحلیل. وجود یکپارچگی‌های پیچیده می‌تواند دستهٔ فناوری مناسب را از CMS ساده به Headless CMS یا Web Application تغییر دهد.

### 3.5 محدودیت بودجه و زمان (Budget & Timeline Constraints)
تعیین سقف واقعی بودجه و زمان تحویل، و انتخاب فناوری‌ای که در این محدوده قابل اجراست. Agent باید هرگز دستهٔ فناوری‌ای را پیشنهاد ندهد که با بودجه/زمان اعلام‌شده توسط کارفرما تناقض آشکار دارد (مثلاً پیشنهاد Web Application سفارشی کامل با بودجهٔ متناسب با یک Landing Page ساده).

### 3.6 نیاز به چندکاناله‌بودن (Omnichannel Requirement)
بررسی اینکه آیا محتوا/داده فقط برای وب‌سایت لازم است یا باید هم‌زمان در اپ موبایل، شبکه‌های دیگر، یا دستگاه‌های دیگر نیز در دسترس باشد. این معیار مستقیماً تعیین‌کنندهٔ نیاز به معماری Headless است.

### 3.7 الزامات امنیتی و انطباق (Security & Compliance)
بر اساس صنعت (طبق سند Industry Patterns)، برخی حوزه‌ها (مثل Healthcare) الزامات امنیتی/قانونی سخت‌گیرانه‌تری دارند که می‌تواند برخی دسته‌های فناوری یا پلتفرم‌های خاص را از انتخاب حذف کند.

### 3.8 توان فنی داخلی تیم/کارفرما (Internal Technical Capability)
ارزیابی اینکه آیا کارفرما یا تیم اجرایی توانایی نگهداری بلندمدت راه‌حل انتخاب‌شده را دارد. راه‌حل‌های با پیچیدگی فنی بالا (Web Application، Headless CMS) نیازمند تیم فنی مستمر هستند؛ در نبود این توان، حتی اگر از نظر فنی «بهتر» باشند، از نظر استراتژیک نامناسب‌اند.

## 4. اصول جلوگیری از پیشنهاد غیرواقعی (Guardrails for Requirement Generation)

1. **هرگز نام محصول قطعی ندهید مگر با شرط:** Agent باید دستهٔ فناوری را پیشنهاد دهد (مثل «CMS سنتی» یا «Headless CMS»)، نه نام ابزار خاص، مگر اینکه کارفرما محدودیت یا ترجیح مشخصی نام برده باشد (مثلاً «باید روی وردپرس باشد»)؛ در آن صورت آن محدودیت باید عیناً رعایت شود.
2. **بودجه/زمان اعلام‌شده هرگز نادیده گرفته نشود:** هیچ توصیهٔ فناوری نباید فرض کند بودجه یا زمان نامحدود است؛ اگر نیاز کارفرما با بودجهٔ اعلام‌شده تناقض دارد، Agent باید این تناقض را صریحاً گزارش کند، نه اینکه راه‌حلی غیرقابل‌اجرا پیشنهاد دهد.
3. **پیچیدگی فناوری باید متناسب با پیچیدگی واقعی مسئله باشد:** انتخاب فناوری پیچیده‌تر از نیاز واقعی (Over-engineering) به‌اندازهٔ انتخاب فناوری ساده‌تر از نیاز (Under-engineering) یک خطای استراتژیک محسوب می‌شود.
4. **توان نگهداری بلندمدت جزئی از تصمیم است، نه فقط ساخت اولیه:** هیچ پیشنهادی نباید فقط بر اساس «امکان ساخت» باشد؛ «امکان نگهداری مستمر توسط کارفرما یا تیم مشخص» باید همیشه بخشی از ارزیابی باشد.
5. **فرضیات فنی باید صریح اعلام شوند:** اگر اطلاعات کافی برای تصمیم‌گیری قطعی (مثل حجم ترافیک موردانتظار) وجود ندارد، Agent باید فرض خود را صریحاً بیان کند («با فرض ترافیک متوسط ماهانه...») به‌جای صدور توصیهٔ قطعی بدون مبنا.
6. **عدم قطعیت فناوری معتبرتر از پیشنهاد نادرست است:** در صورت کمبود اطلاعات کافی از کارفرما (مثل نامشخص‌بودن فرکانس به‌روزرسانی محتوا)، Agent باید این را به‌عنوان سوال باز به کارفرما ارجاع دهد، نه اینکه فرضی دلبخواهی را مبنای Requirement نهایی قرار دهد.

## 5. جدول خلاصهٔ نگاشت به اسناد قبلی (برای استفادهٔ یکپارچهٔ AI)

| ورودی از سند قبلی | تأثیر روی تصمیم فناوری |
|---|---|
| Website Type = Marketplace/SaaS/Web Application (از Website Types) | معمولاً نیازمند Web Application یا ترکیب Headless CMS + Web App |
| Website Type = Corporate/Portfolio/Landing Page | معمولاً کافی است با CMS سنتی یا Static Website پوشش داده شود |
| Website Type = Ecommerce | ابتدا Ecommerce Platform بررسی شود؛ فقط در صورت نیاز غیراستاندارد به Web App اختصاصی رجوع شود |
| فرکانس بالای تولید محتوا (از Content Strategy) | اولویت با CMS یا Headless CMS به‌جای Static Website |
| نیاز صنعتی به امنیت بالا (از Industry Patterns، مثل Healthcare) | بررسی دقیق‌تر گزینه‌ها از منظر انطباق امنیتی، صرف‌نظر از دستهٔ فناوری انتخاب‌شده |
| نیاز به چند کانال محتوایی | تمایل به‌سمت Headless CMS |
