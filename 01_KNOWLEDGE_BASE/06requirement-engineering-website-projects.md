# مهندسی نیازمندی برای پروژه‌های وب‌سایت (Requirement Engineering)
### سند مرجع برای تبدیل خودکار داده‌های مصاحبه به خروجی قابل‌استفادهٔ تیم فنی

مدل هسته: `Customer Answer → Insight → Decision → Requirement`

---

## نحوه استفاده از این سند توسط Agent

این سند مرحلهٔ بعد از سند «متدولوژی مصاحبه» است: ورودی آن پاسخ‌های برچسب‌گذاری‌شدهٔ مشتری (FACT / HYPOTHESIS / OPINION) است و خروجی آن سندی است که مستقیم قابل تحویل به تیم فنی (توسعه‌دهنده، طراح، دواپس) باشد. هر بخش شامل **قانون تبدیل** و **قالب خروجی** است.

---

## ۱. مدل تبدیل: از پاسخ مشتری تا Requirement

### چرا این چهار لایه لازم است
اگر مستقیم از «پاسخ مشتری» به «Requirement» پریده شود، دو خطر وجود دارد: (۱) نیازمندی بر پایهٔ یک نظر یا ادعای تأییدنشده ساخته می‌شود، (۲) ارتباط نیازمندی با دلیل وجودی‌اش گم می‌شود و تیم فنی نمی‌داند «چرا» این را می‌سازد. لایه‌های میانی (Insight و Decision) این خلأ را پر می‌کنند و **ردیابی‌پذیری (Traceability)** ایجاد می‌کنند — چیزی که در متدولوژی‌های استاندارد مهندسی نیازمندی (Elicitation → Analysis → Specification → Validation) هم به همین ترتیب تأکید می‌شود.

### تعریف هر لایه

| لایه | تعریف | مثال |
|---|---|---|
| **Customer Answer** | گفتهٔ خام مشتری، دست‌نخورده، با برچسب FACT/HYPOTHESIS/OPINION (طبق سند مصاحبه) | «هفتهٔ پیش سه مشتری با ایمیل سؤال قیمت پرسیدند و دو روز طول کشید جواب بدهم.» [FACT] |
| **Insight** | الگوی معنادار استخراج‌شده از یک یا چند پاسخ؛ هنوز راه‌حل نیست، فقط فهم است | «مشتریان بالقوه در انتظار پاسخ قیمت، طولانی معطل می‌مانند و این می‌تواند به از دست رفتن لید بینجامد.» |
| **Decision** | انتخاب راهبردی تیم دربارهٔ اینکه با این Insight چه باید کرد (هنوز مشخصات فنی نیست) | «باید مسیر دریافت اطلاعات قیمت/تماس برای کاربر سریع‌تر و در دسترس‌تر شود.» |
| **Requirement** | مشخصهٔ دقیق، قابل‌اجرا، قابل‌تست که تیم فنی می‌سازد | «سیستم باید یک صفحهٔ Pricing عمومی با فرم درخواست تماس ارائه دهد؛ زمان پاسخ فرم حداکثر ۲۴ ساعت اعلام شود.» |

### قانون کلیدی تبدیل: هر لایه باید توسط لایهٔ قبلی توجیه‌پذیر باشد
هیچ Requirement نباید بدون یک Decision پشت آن نوشته شود؛ هیچ Decision نباید بدون یک Insight گرفته شود؛ هیچ Insight نباید فقط بر اساس یک پاسخ OPINION یا COMPLIMENT ساخته شود (طبق سند مصاحبه).

### جدول قانون برای Agent
| ورودی | بررسی قبل از عبور به لایهٔ بعد |
|---|---|
| Customer Answer → Insight | آیا پاسخ FACT است یا حداقل با چند FACT دیگر هم‌راستا است؟ اگر فقط OPINION/COMPLIMENT است، Insight ساخته نشود |
| Insight → Decision | آیا این Insight با هدف کسب‌وکار (بخش Business/Goal مصاحبه) مرتبط است؟ اگر نه، به Backlog «نیازمند بررسی بیشتر» برود |
| Decision → Requirement | آیا Decision به‌اندازهٔ کافی مشخص است که به Functional/Content/UX/Technical تبدیل شود؟ اگر کلی است، ابتدا باید دقیق‌تر شود |

### قالب رکورد ردیابی‌پذیری (Traceability Record) — برای هر Requirement
```
ID: REQ-XXX
Customer Answer(s) مرتبط: [شناسهٔ پاسخ‌ها از رونوشت مصاحبه]
Insight: ...
Decision: ...
Requirement (نهایی): ...
نوع: Functional / Content / UX / Technical
اولویت: Must / Should / Nice-to-have / Don't Build
```
این قالب تضمین می‌کند تیم فنی هر زمان بخواهد بداند «چرا این ساخته می‌شود»، بتواند مستقیم به پاسخ اصلی مشتری برگردد.

## ۲. انواع Requirement برای پروژه‌های وب‌سایت

### الف) Functional Requirement (نیازمندی عملکردی)
**تعریف:** آنچه سیستم باید «انجام دهد» — رفتار، ورودی/خروجی، منطق. معمولاً به فرم «سیستم باید بتواند...» نوشته می‌شود و باید قابل تست باشد.

**مثال‌های وب‌سایتی:**
- سیستم باید فرم تماس را با اعتبارسنجی ایمیل و شمارهٔ تلفن ارائه دهد.
- کاربر باید بتواند در نمونه‌کارها بر اساس دسته‌بندی فیلتر کند.
- سیستم باید پس از ثبت فرم، یک ایمیل تأیید خودکار برای کاربر ارسال کند.
- ادمین باید بتواند مقالات بلاگ را بدون نیاز به دانش کدنویسی ویرایش کند (نیاز به CMS).

### ب) Content Requirement (نیازمندی محتوایی)
**تعریف:** چه محتوایی، با چه ساختار و چه حجمی، باید در سایت وجود داشته باشد — شامل متن، تصویر، ویدیو، داده‌های ساختاریافته (مثل قیمت، مشخصات).

**مثال‌های وب‌سایتی:**
- صفحهٔ اصلی باید شامل یک Headline که مسئلهٔ مشتری هدف را در ۱ جمله بیان کند.
- هر پروژهٔ نمونه‌کار باید شامل: مسئله، راه‌حل، نتیجهٔ کمی (حداقل یک عدد) باشد.
- صفحهٔ About باید معرفی تیم با عکس واقعی داشته باشد (نه Stock Photo).
- سایت باید حداقل به دو زبان (فارسی/انگلیسی) محتوای صفحات اصلی را داشته باشد.

### پ) UX Requirement (نیازمندی تجربهٔ کاربری)
**تعریف:** چگونگی تعامل، ناوبری، جریان کاربر و سلسله‌مراتب بصری — مستقل از پیاده‌سازی فنی دقیق، اما وابسته به رفتار کاربر.

**مثال‌های وب‌سایتی:**
- فاصلهٔ بین ورود کاربر و رسیدن به فرم تماس/قیمت باید حداکثر ۲ کلیک باشد.
- در موبایل، دکمهٔ CTA اصلی باید در ناحیهٔ قابل‌دسترس با انگشت شست (Thumb Zone) باشد.
- کاربر باید بدون گم‌شدن بتواند از هر صفحهٔ خدمت به صفحهٔ نمونه‌کار مرتبط برسد.
- فرم چندمرحله‌ای نباید بیش از ۳ مرحله داشته باشد و باید Progress Indicator نشان دهد.

### ت) Technical Requirement (نیازمندی فنی)
**تعریف:** الزامات زیرساختی، عملکردی-کیفی (Non-Functional) و محدودیت‌های پیاده‌سازی — کارایی، امنیت، مقیاس‌پذیری، سازگاری، یکپارچه‌سازی. این‌ها معمولاً همان «ity»هایی هستند که کیفیت سیستم را تعیین می‌کنند نه رفتار مستقیم آن.

**مثال‌های وب‌سایتی:**
- زمان بارگذاری صفحهٔ اصلی باید زیر ۲.۵ ثانیه در موبایل باشد (معیار: Core Web Vitals — LCP).
- سایت باید در برابر ۱۰٬۰۰۰ بازدید هم‌زمان بدون افت کارایی پایدار بماند.
- سایت باید با استانداردهای HTTPS و امنیت پایه (فرم‌ها در برابر اسپم محافظت‌شده) مطابق باشد.
- سایت باید با CRM موجود مشتری (مثلاً HubSpot) یکپارچه شود.
- سایت باید در مرورگرهای اصلی و حداقل دو نسخهٔ اخیر iOS/Android به‌درستی نمایش داده شود.

### جدول تشخیص نوع Requirement برای Agent
| اگر Decision دربارهٔ... باشد | نوع Requirement |
|---|---|
| یک رفتار/عملکرد مشخص سیستم | Functional |
| چه چیزی روی صفحه نوشته/نمایش داده شود | Content |
| مسیر/تجربهٔ حرکت کاربر، سلسله‌مراتب، احساس تعامل | UX |
| سرعت، امنیت، مقیاس، یکپارچگی با سیستم دیگر، سازگاری دستگاه | Technical |

> نکته: بسیاری از Decisionها هم‌زمان به چند نوع Requirement تبدیل می‌شوند. مثلاً Decision «کاهش زمان انتظار مشتری برای قیمت» می‌تواند هم‌زمان یک UX Requirement (کاهش کلیک تا فرم)، یک Functional Requirement (فرم درخواست قیمت با پاسخ خودکار)، و یک Technical Requirement (اتصال فرم به CRM برای پاسخ سریع) تولید کند.

## ۳. چگونه Requirementها اولویت‌بندی شوند؟ (مدل MoSCoW تطبیق‌یافته)

### تعریف چهار سطح
| سطح | تعریف | آزمون تشخیص |
|---|---|---|
| **Must Have** | بدون آن، پروژه به هدف اصلی‌اش نمی‌رسد یا اصلاً قابل راه‌اندازی نیست | «اگر این نباشد، آیا پروژه شکست‌خورده تلقی می‌شود؟» اگر پاسخ بله است → Must |
| **Should Have** | مهم و بااثر روی هدف، اما راه‌اندازی بدون آن هم ممکن است (با یک راه‌حل موقت/دستی) | «اگر نباشد، چقدر درد ایجاد می‌کند و برای چند نفر؟» درد بالا/گسترده → Should |
| **Nice to Have** | ارزش می‌افزاید ولی اثر کم روی هدف اصلی دارد؛ اگر زمان/بودجه اجازه داد | «آیا حذفش کسی را واقعاً اذیت می‌کند؟» نه چندان → Nice to Have |
| **Don't Build** | یا خارج از هدف پروژه است، یا هزینه/ریسکش به‌وضوح از ارزش آن بیشتر است، یا مبتنی بر یک HYPOTHESIS تأییدنشده است که با شواهد فعلی توجیه ندارد | «آیا این ایده صرفاً یک فرضیهٔ اثبات‌نشده یا خواستهٔ حاشیه‌ای است؟» بله → Don't Build |

### اصول عملی اولویت‌بندی
- **معیار عینی تعیین کن، نه احساسی:** بدون تعریف روشنِ «Must یعنی چه»، معمولاً بیشتر آیتم‌ها به‌اشتباه Must علامت می‌خورند؛ باید صریحاً از قبل توافق شود.
- **آزمون «راه‌حل موقت»:** اگر بدون این Requirement بتوان با یک راهکار دستی/موقت ادامه داد (even با درد)، Requirement از Must به Should تنزل می‌کند.
- **تعادل حجمی:** طبق تجربهٔ رایج در چارچوب DSDM، تلاش تیم روی «Must Have»ها بهتر است از حدود ۶۰٪ کل تلاش پروژه بیشتر نشود؛ در غیر این صورت ریسک شکست پروژه (به‌خاطر عدم انعطاف) بالا می‌رود.
- **پیوند مستقیم به Decision/Insight:** هر Requirement بدون یک Decision پشتیبان که به یک Insight مبتنی بر FACT برسد، نباید به‌راحتی Must شود — چون معمولاً یعنی بر پایهٔ فرض ساخته شده.
- **جداسازی صریح Don't Build:** این سطح نباید نادیده گرفته شود یا حذف شود؛ باید صراحتاً ثبت و به مشتری/تیم اعلام شود تا انتظارات مدیریت شود و بعداً به‌عنوان «فراموش‌شده» دوباره مطرح نشود.

### جدول قانون تصمیم‌گیری خودکار برای Agent
| شرط دربارهٔ Requirement | اولویت پیشنهادی |
|---|---|
| مستقیماً به هدف اصلی پروژه (Goal) وصل است و بدون آن هدف اصلی محقق نمی‌شود | Must Have |
| به یک Insight مبتنی بر چند FACT هم‌راستا وصل است ولی راه‌حل موقت دارد | Should Have |
| فقط برای یک نفر/یک مورد خاص کاربردی است یا اثر جانبی کوچک دارد | Nice to Have |
| فقط بر پایهٔ یک HYPOTHESIS یا COMPLIMENT تأییدنشده است، بدون FACT پشتیبان | Don't Build (یا بازگشت به فاز Discovery برای اعتبارسنجی بیشتر) |
| خارج از محدودهٔ Business/Goal تعریف‌شده در Discovery است | Don't Build |
| هزینهٔ فنی/زمانی بسیار بالاتر از ارزش تخمینی آن است | Don't Build یا Should Have (بسته به قابل‌تفکیک بودن هزینه) |

## ۴. قالب خروجی نهایی برای تیم فنی

هدف این بخش، تولید سندی است که مستقیم قابل تحویل به تیم فنی باشد — بدون نیاز به تفسیر اضافه.

### ساختار پیشنهادی سند نهایی (Requirement Specification)

```
## REQ-001
نوع: Functional
عنوان: فرم درخواست قیمت با پاسخ خودکار
شرح: سیستم باید یک فرم درخواست قیمت در صفحهٔ Pricing ارائه دهد که شامل نام، ایمیل، 
     شرح نیاز باشد؛ پس از ارسال، ایمیل تأییدی با اعلام «حداکثر ۲۴ ساعت پاسخ» ارسال شود.
اولویت: Must Have
منبع (Traceability):
  - Customer Answer: "هفتهٔ پیش سه مشتری با ایمیل سؤال قیمت پرسیدند و دو روز طول کشید جواب بدهم." [FACT]
  - Insight: مشتریان بالقوه در انتظار پاسخ قیمت معطل می‌مانند و ممکن است از دست بروند.
  - Decision: مسیر دریافت اطلاعات قیمت باید سریع‌تر و در دسترس‌تر شود.
معیار پذیرش (Acceptance Criteria):
  - فرم اعتبارسنجی فیلدها را انجام دهد
  - ایمیل تأیید ظرف کمتر از ۱ دقیقه پس از ارسال دریافت شود
  - داده‌های فرم در سیستم مدیریت لید ذخیره شود
وابستگی فنی: نیاز به اتصال به سرویس ایمیل / CRM
```

### جدول ستون‌های الزامی سند نهایی (برای هر Requirement)
| ستون | توضیح |
|---|---|
| ID | شناسهٔ یکتا برای ردیابی در بک‌لاگ/تیکت |
| نوع | Functional / Content / UX / Technical |
| عنوان | یک‌خطی، قابل‌فهم برای غیرفنی |
| شرح دقیق | قابل‌تست، بدون ابهام، بدون فعل مبهم («بهتر»، «سریع‌تر» بدون عدد ممنوع) |
| اولویت | Must / Should / Nice-to-have / Don't Build |
| منبع (Traceability) | زنجیرهٔ Answer → Insight → Decision |
| معیار پذیرش | چطور تیم QA/فنی تأیید کند که ساخته شده و درست کار می‌کند |
| وابستگی فنی | سرویس‌ها، APIها، دیتابیس، یکپارچه‌سازی‌های لازم |

### قانون کیفیت نوشتن Requirement برای Agent
| قانون | مثال نقض | اصلاح‌شده |
|---|---|---|
| باید قابل تست باشد | «سایت باید سریع باشد» | «زمان بارگذاری صفحهٔ اصلی زیر ۲.۵ ثانیه (LCP) در موبایل» |
| نباید راه‌حل فنی را زودتر از لازم دیکته کند مگر ضروری باشد | «باید از React استفاده شود» (بدون دلیل فنی) | «سیستم باید تعاملات پویا و سریع در فرم چندمرحله‌ای پشتیبانی کند» (تیم فنی ابزار را انتخاب کند) |
| باید فعل مشخص و اندازه‌گیری‌پذیر داشته باشد | «تجربهٔ کاربری بهتر شود» | «فاصله تا CTA اصلی حداکثر ۲ کلیک» |
| باید فقط یک نیاز را توصیف کند (Atomic) | «فرم تماس و صفحهٔ پرسش‌های متداول و چت آنلاین اضافه شود» | سه Requirement جدا با اولویت‌های احتمالاً متفاوت |

## خلاصهٔ منطق کامل Agent (اتصال سه سند: Interview → Requirement → Prioritization)

```
[Interview Agent]
   → پاسخ خام + برچسب FACT/HYPOTHESIS/OPINION/COMPLIMENT
        ↓
[Requirement Agent]
   1. فیلتر: فقط FACT و HYPOTHESISهای هم‌راستا با چند FACT وارد مرحلهٔ Insight شوند
   2. تولید Insight (الگوی معنادار، نه راه‌حل)
   3. تبدیل Insight به Decision (راهبرد، هنوز نه مشخصات فنی)
   4. تبدیل Decision به یک یا چند Requirement با نوع مشخص (Functional/Content/UX/Technical)
   5. ثبت زنجیرهٔ Traceability برای هر Requirement
        ↓
[Prioritization Agent]
   6. اعمال آزمون‌های Must/Should/Nice-to-have/Don't Build روی هر Requirement
   7. بررسی تعادل حجمی (Must ≤ ~60٪ تلاش کل)
   8. تولید سند نهایی با قالب بخش ۴ برای تحویل به تیم فنی
```

### جدول قوانین کنترل کیفیت نهایی برای Agent
| بررسی | هدف |
|---|---|
| آیا هر Requirement حداقل یک Traceability Record دارد؟ | جلوگیری از Requirement بی‌ریشه |
| آیا هیچ Requirement صرفاً بر پایهٔ COMPLIMENT ساخته نشده؟ | جلوگیری از ساخت بر پایهٔ ادب اجتماعی مشتری |
| آیا نوع هر Requirement به‌درستی از میان چهار دسته تعیین شده؟ | جلوگیری از ابهام برای تیم فنی |
| آیا هر Requirement معیار پذیرش قابل‌تست دارد؟ | جلوگیری از ابهام در QA |
| آیا سهم Must Have از کل کمتر از ~۶۰٪ تلاش تخمینی است؟ | کاهش ریسک شکست پروژه |
